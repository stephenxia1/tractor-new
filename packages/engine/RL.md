# RL bot — `rl-mlp`

A small REINFORCE-trained policy that ships as a `BotType` like any other
built-in. This document explains how the agent is structured, how it
trains, how trained weights get into the shipped bundle, and what to know
before changing it.

> Companion docs: [`API.md`](./API.md) (engine contract),
> [`ADDING_AGENTS.md`](./ADDING_AGENTS.md) (the generic recipe for new
> bots — the RL bot follows it). Read those first if you haven't.

---

## 1. What it is

- **Algorithm**: REINFORCE (vanilla policy-gradient) with an EMA reward
  baseline.
- **Policy**: per-candidate scoring. At each play decision, the engine's
  `legalActions(state, seat)` is filtered to `play_cards` candidates,
  each is reduced to a feature vector, and the policy outputs a scalar
  score. Softmax over the scores defines the action distribution. Sample
  during training; argmax during eval.
- **Model**: small MLP (32 → 64 ReLU → 1 scalar). ~2.2k parameters.
- **Training rig**: in-process self-play via the engine's
  `runHand`/`runMatch` driver. No Python, no external ML deps.
- **Pre-play**: declare/kitty/non-turn phases delegate to
  `pickBotAction('lowball')`. Only the in-trick play is learned.

The bot's ceiling is intentionally modest. It crushes `random` and
`lowball` but loses to the hand-engineered `smart` / `smart-v2`
heuristics. Treat this as the seed RL pipeline; the `plan.md` Python PPO
roadmap is where stronger agents will come from.

## 2. File layout

All files live in `packages/engine/src/rl/mlp/`:

| File                  | Role                                                                 |
| --------------------- | -------------------------------------------------------------------- |
| `features.ts`         | Per-candidate feature extractor. Defines `FEATURE_DIM` (= 32).        |
| `policy.ts`           | MLP forward + backward, softmax + sampling, Adam, JSON serialization. |
| `agent.ts`            | Glue to the engine `Agent` contract; defers non-play to `lowball`.    |
| `train.ts`            | REINFORCE self-play trainer. Runnable script.                         |
| `eval.ts`             | Trained policy vs `random` (and `lowball` reference). Runnable.       |
| `eval-integrated.ts`  | Same but routed through `pickBotAction('rl-mlp')`. Runnable.          |
| `weights.json`        | Auto-generated by `train.ts` — trained parameters as JSON.            |
| `embeddedWeights.ts`  | Auto-generated by `train.ts` — same parameters as a TS module so      |
|                       | `bot.ts` can import them without filesystem I/O (web bundle safety). |

Wiring into the broader engine (in `packages/engine/src/bot.ts`):

- `'rl-mlp'` is added to `BotType`, `BOT_TYPES`, and `botTypeLabel`.
- `pickBotAction` dispatches `'rl-mlp'` to a lazy singleton built from
  `EMBEDDED_WEIGHTS` + `makePolicyAgent({ mode: 'eval' })`.

That's the entire ship surface — no other engine, server, or UI file
needs to know.

## 3. State / feature representation

The decision unit is **one candidate move**. For each candidate we
produce a fixed-dim feature vector, then score them all and softmax.
This sidesteps the combinatorial action-space problem (52-card hands,
variable-length combos): we only need the policy to *rank* the
already-legal candidates that `legalActions` returns.

`buildDecisionContext(state, seat)` is computed once per decision and
captures global signals (hand size, attackerPoints, who's winning the
trick, etc.). `extractFeatures(cards, tags, ctx)` then writes a
32-element `Float64Array` per candidate.

The 32 features (see `features.ts` for ground truth):

```
 0      bias (constant 1)
 1      candidate card count / 8
 2      sum of point-card values in candidate / 30
 3      max natural rank in candidate / 13
 4      min natural rank in candidate / 13
 5      candidate is all-trump
 6      candidate contains a joker
 7      candidate contains a trump-rank card
 8      candidate contains a same-key pair
 9-15   tag one-hot (lead-single/pair/tractor/throw-safe,
                     follow-led-suit/trump/discard)
16-20   effective-suit one-hot (♠/♥/♦/♣/trump)
21      is leading (trick === null)
22      tricks remaining / 25
23      attackerPoints / 200
24      my team is attackers
25      trump fraction of my hand
26      hand size / 25
27      seat position in trick / 4
28      points already in this trick / 30
29      candidate would beat current trick winner (follow only)
30      teammate is currently winning
31      I am the landlord
```

Tag info comes straight from `legalActions`'s `tags` field, which is
why we filter to `kind === 'play_cards'` and pass the candidate's tags
through.

## 4. Policy architecture

```
score = W2 · ReLU(W1 · feature_vec + b1) + b2
```

Stored as one flat `Float64Array` of length `PARAM_COUNT` for cache
locality. Layout: `[W1 (HIDDEN×FEATURE_DIM, row-major) | b1 | W2 | b2]`.

Softmax with temperature τ over the per-candidate scores defines the
action distribution. During training τ = 1.0 (sample); during eval
τ = 0.05 (effectively argmax).

### REINFORCE gradient

For one decision with sampled index `k*`:

```
∇θ log π(k*) = Σ_j (1[j == k*] − π(j)) / τ · ∇θ score_j
```

This is computed over **all** candidates, not just the sampled one, because
the softmax denominator depends on every score. Each `∇θ score_j` flows
through the cached forward activations, so backprop costs ~one forward
pass per candidate per decision — implemented in
`accumulateScoreGradient` and `accumulateReinforceGradient` in
`policy.ts`.

The full per-decision gradient is multiplied by `(reward − baseline)` and
accumulated into one buffer per episode, then averaged across decisions
before the Adam step. Gradient clipping (default global L2 norm 5.0)
guards against blow-ups.

## 5. Training loop

Per-episode flow in `train.ts`:

1. **Pick which team is "ours"** for this episode (random A or B). Both
   seats of that team use the current policy; the other team is filled
   with opponents. Putting current policy on a single team avoids
   gradient cancellation between mirror-image perspectives.
2. **Sample opponents** for the other two seats: with p=0.5 a snapshot
   of a past version of the policy, otherwise one of `lowball`,
   `aggressive`, `point-hoarder`, `random`. (Snapshots run with
   temperature 0.5 so they stay slightly stochastic.)
3. **Play one hand** via `runHand`. The current-policy agent records
   `(per-candidate cache, sampled idx, probs, temperature)` for every
   decision into a per-seat trajectory.
4. **Compute the per-team reward** from the hand summary:
   `clip((attackerPoints − 80) / 80, −1, 1)` for attackers; negate for
   defenders. Same reward applies to every decision in the hand for
   that seat — no per-trick credit assignment in v1.
5. **Update the EMA baseline** with the team's reward. The advantage
   `(reward − baseline)` is what scales the policy-gradient update.
6. **Accumulate the gradient** across all our-policy decisions in the
   episode, average over decision count, clip, Adam-step.
7. **Snapshot** every `SNAPSHOT_EVERY` (default 250) episodes; keep the
   last 5. **Eval** every `EVAL_EVERY` episodes against `random` to log
   progress.

### Hyperparameters

Defaults baked into `train.ts`; all overridable via env vars:

| env var          | default | meaning                                  |
| ---------------- | ------- | ---------------------------------------- |
| `EPISODES`       | 8000    | Total training episodes                  |
| `LR`             | 5e-4    | Adam learning rate                       |
| `BASELINE_EMA`   | 0.99    | Reward baseline EMA decay                |
| `TRAIN_TEMP`     | 1.0     | Softmax temperature during training      |
| `EVAL_TEMP`      | 0.05    | Softmax temperature during eval (≈argmax)|
| `SNAPSHOT_EVERY` | 250     | Episodes between snapshot pool updates   |
| `SNAPSHOT_POOL_MAX` | 5    | Max snapshots retained                   |
| `EVAL_EVERY`     | 1000    | Episodes between progress evals          |
| `EVAL_GAMES`     | 30      | Games per progress eval                  |
| `EVAL_MAX_HANDS` | 30      | Hand cap per progress-eval game          |
| `GRAD_CLIP`      | 5.0     | Global L2 gradient norm cap              |
| `SEED`           | 17      | PRNG seed (everything is deterministic)  |
| `WEIGHTS_OUT`    | (auto)  | Override output JSON path                |
| `RESUME_FROM`    | (none)  | Continue from a saved JSON               |

Throughput on a laptop: ~100–140 episodes/sec. 8k episodes ≈ 60–100s.

## 6. Trained → shipped

Two artifacts come out of training:

- **`weights.json`** — for inspection, tooling, version control diffs.
- **`embeddedWeights.ts`** — auto-generated TS module exporting the same
  parameters as a typed const. **This is what `bot.ts` imports.**

Why two? The web bundle (`apps/web`) imports the engine as TS source.
Reading from the filesystem at module-init time would break in browsers.
Embedding the weights into a TS module sidesteps that without forcing
us to enable JSON imports or a build-time loader.

`bot.ts` builds the agent lazily on first use:

```ts
let _rlMlpAgent: ((s: GameState, seat: Seat) => BotAction) | null = null;
function rlMlpAgent() {
  if (_rlMlpAgent === null) {
    const policy = deserializeRlPolicy(EMBEDDED_RL_WEIGHTS);
    _rlMlpAgent = makeRlPolicyAgent({ policy, mode: 'eval' });
  }
  return _rlMlpAgent;
}
```

The MLP is stateless across decisions, so one singleton serves every
`'rl-mlp'` seat in every concurrent game.

`deserialize` validates that `featureDim` and `hidden` in the weights
file match the constants compiled into the source. If anyone edits
`features.ts` or `policy.ts` in a way that changes the feature count or
hidden width without re-training, the bot will throw at first use
instead of silently misbehaving.

## 7. Common workflows

### Re-train

```sh
cd packages/engine
EPISODES=20000 ../../node_modules/.bin/tsx src/rl/mlp/train.ts
```

Both `weights.json` and `embeddedWeights.ts` are overwritten. To use
the new weights in the engine, just re-import — no other step needed.

### Evaluate

Two scripts:

- `eval.ts` runs the policy via `makePolicyAgent` directly. Fast iteration
  during development.
- `eval-integrated.ts` routes through `pickBotAction('rl-mlp')`. This
  is the path the WS server / UI uses; run it to verify integration.

```sh
NUM_GAMES=200 MAX_HANDS=50 ../../node_modules/.bin/tsx src/rl/mlp/eval-integrated.ts
```

Reports wins, attacker-points avg, hands-per-game, stalemates against
each baseline (random / lowball / smart / smart-v2).

### Add to the existing test suite

`packages/engine/test/bot.test.ts` already exercises bots end-to-end
with `runFullHandWithBots`. Adding an `'rl-mlp'` case there is the
standard regression smoke test.

## 8. Known limitations & next steps

1. **Candidate pool is what `legalActions` returns.** That's a curated,
   small subset — not the full legal action space. A stronger policy
   would either widen the candidate enumerator or learn to construct
   actions from primitives (much harder).
2. **No partial-information modeling.** The policy looks at full state
   (including opponents' hands, exposed in self-play). Inference also
   gets full state today. For a competitive online bot, this would need
   to be re-trained on perspective-restricted observations.
3. **Per-hand reward, no per-trick credit assignment.** Variance is
   high; a trick-level baseline or GAE would help.
4. **No critic.** REINFORCE + EMA baseline only. PPO with a centralized
   critic (per `plan.md`) is the planned upgrade and would lift the
   ceiling substantially.
5. **Pre-play (declare, kitty bury) is hand-coded `lowball` logic.**
   Both phases are high-leverage in real play; learning them is future
   work.
6. **Loses to `smart` / `smart-v2`.** Those are search-based heuristics
   that did not exist as opponents during training and have nontrivial
   one-ply lookahead. Beating them likely needs more model capacity,
   more episodes, and ideally adversarial inclusion of `smart-v2` in
   the opponent pool (note: `smart-v2` is slow due to per-decision
   simulation, so opponent-pool inclusion has a real wall-clock cost).

If you tighten any of (1)–(6), please update this doc and the eval
table in your PR description.
